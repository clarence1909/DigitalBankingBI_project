# Data sources

The six source systems behind the Kelip Bank warehouse: what each one holds, its format and grain, the problems in it, and the rule that cleans each problem. The rules are carried out in the staging layer ([`sql/01_staging/`](../sql/01_staging/)), one SQL file per source table, and each file repeats its rules in its header.

> **All data is synthetic.** The sources are generated by a seeded Python simulator ([`src/generate/`](../src/generate/)). A small sample of each one is committed in [`data/sample/`](../data/sample/) so you can see the formats without running anything; the full files are rebuilt in `data/raw/` by `python run_pipeline.py`.

## 2. How sources are loaded

The load stage ([`src/load.py`](../src/load.py)) copies every source into the `raw` schema of the DuckDB warehouse **as text**, exactly as it arrived, and records each file's row count in `raw._load_log`. Nothing is typed, cleaned or dropped on the way in, so:

- a bad value can never stop the load, and every cleaning rule is visible in SQL rather than hidden in a loader;
- the staging layer can be rerun from the raw copy without touching the files again;
- a check can always count what staging removed against what arrived (`duplicates_removed_in_staging`).

The warehouse session is pinned to UTC, so a timestamp without an offset is read the same way on a laptop in Malaysia and on a CI runner in UTC. Money is converted from text to exact decimals (`DECIMAL(18,2)`), never floating point, so totals tie to the sen.

## 3. The six sources

### 1. Mobile app analytics: `app_events.json.gz`

The app sends an event at each step of sign-up. Each line is one JSON object with nested `context` (channel, device, app version) and `properties` (eKYC flow, attempt number, reason, customer ID) objects.

**Fields:** `event_id`, `event_name` (signup_started, phone_verified, id_scanned, liveness_failed, liveness_passed, ekyc_approved, ekyc_rejected, account_opened), `event_ts`, `received_at`, `applicant_id`, `context`, `properties`.

| Problem in the source | Cleaning rule | Where |
|---|---|---|
| The app retries sends, so an event can arrive twice | Keep the first copy received (`QUALIFY row_number() ... = 1`) | `stg_app_events.sql` |
| Timestamps come in UTC (`...Z`) or, from the old Android app, as local time with an offset (`...+08:00`) | Parse both to the same instant, then convert to Malaysia time | `stg_app_events.sql` |
| Channel labels differ between SDK versions (`tiktok`, `tik_tok`, `TIKTOK`; `fb`, `IG`, `facebook`) | Map through `reference.channel_map`; a check fails if any label is unmapped | `stg_app_events.sql` |
| The eKYC flow flag only exists from the A/B test onwards | A missing flag means the control flow, which everyone saw before the test | `stg_app_events.sql` |

The staged events feed `marts.fct_onboarding_funnel`, which keeps one row per applicant with the time each step was reached.

### 2. Core banking: `customers.csv`, `accounts.csv`, `account_balances.csv.gz`

The bank's system of record for customers, their accounts, and each account's balance at month end.

**Fields:** customers have `customer_id`, `applicant_id`, `open_date`, `birth_year`, `state`, `employment_type`, `monthly_income_band`, `risk_rating`, `fraud_flag_date`, `customer_status`, `last_updated_at`. Accounts have `account_id`, `customer_id`, `product_code`, dates, status, and for fixed deposits the rate, principal, tenor, maturity date, campaign code and the deposit it rolled over from. Balances have `account_id`, `balance_date`, `ledger_balance`.

| Problem in the source | Cleaning rule | Where |
|---|---|---|
| Customer dates are DD/MM/YYYY | Parse with an explicit format | `stg_customers.sql` |
| A re-extract left 95 customers in the file twice | Keep the most recently updated row | `stg_customers.sql` |
| State and employment are partly free text (`SELANGOR`, `Selangor Darul Ehsan`) | Map through `reference.state_map` and `reference.employment_map` | `stg_customers.sql` |
| Product codes vary in format (`SAV-01`, `SAV01`, `sav-01`) | Map through `reference.product_map` | `stg_accounts.sql` |
| Empty strings stand for missing values | Convert to NULL | `stg_accounts.sql` |

Month-end balances are the core banking view of each account; reconciliation 1 checks them against the ledger, account by account and month by month.

### 3. Posting engine: `ledger_postings.parquet`

Every movement of money on a savings or fixed deposit account: salary in, DuitNow transfers in and out, bill payments, card purchases, interest, fixed deposit placements and maturities, and personal financing paid out and repaid.

**Fields:** `posting_id`, `account_id`, `posting_ts` (UTC), `amount` (unsigned), `direction` (CR or DR), `txn_code`, `channel`, `reference` (the card authorisation or loan it belongs to).

| Problem in the source | Cleaning rule | Where |
|---|---|---|
| Timestamps are UTC, but month end is Malaysia time: a posting at 18:00 UTC on the last day of a month is in the next month in Malaysia | Convert to Malaysia time before taking the date and month | `stg_ledger_postings.sql` |
| The engine was upgraded on 1 June 2025 and switched from long codes (`DUITNOW_OUT`) to short ones (`DNO`) | Map both through `reference.txn_code_map` | `stg_ledger_postings.sql` |
| Amounts are unsigned with a direction | `signed_amount` is positive for credits and negative for debits | `stg_ledger_postings.sql` |

Getting the time zone wrong would put about 53,000 account-months out of balance; reconciliation 1 catches it.

### 4. Card processor: `card_authorisations.csv.gz`

Every debit card authorisation, from the processor's daily file.

**Fields:** `auth_id`, `card_id`, `auth_ts`, `amount`, `mcc` (merchant category code), `merchant_category`, `entry_mode`, `response_code`, `status`, `settlement_date` (YYYYMMDD), `record_updated_at`.

| Problem in the source | Cleaning rule | Where |
|---|---|---|
| `auth_ts` is UTC with no offset | Read it explicitly as UTC, then convert to Malaysia time | `stg_card_authorisations.sql` |
| Status updates (such as a reversal) and resends arrive as extra rows for the same `auth_id` | Keep the latest record | `stg_card_authorisations.sql` |
| Status, entry mode and merchant labels are inconsistent | Map statuses and entry modes through reference tables; take the category from the MCC code, not the free-text label | `stg_card_authorisations.sql` |
| Some purchases settle days after authorisation, some in the next month | Keep both dates; card spend is reported by settlement (the ledger view), and a check reports the timing differences | `stg_card_authorisations.sql`, check `late_card_settlements` |

Reconciliation 2 checks that every settled authorisation posts to the ledger once, for the same amount, on its settlement date, and that nothing posts without one.

### 5. Loan management system: `loans.parquet`, `loan_tape.parquet`

Personal financing, from January 2025: one row per loan at origination, and a month-end tape with each loan's balance and arrears.

**Fields:** loans have `loan_id`, `customer_id`, `application_date`, `disbursement_date`, `principal`, `tenor_months`, `interest_rate_pct`, `risk_grade`, `credit_policy_code`, `dsr_pct` (debt service ratio). The tape has `loan_id`, `snapshot_date`, `outstanding_principal`, `instalments_due`, `instalments_paid`, `days_past_due`, `loan_status`.

| Problem in the source | Cleaning rule | Where |
|---|---|---|
| Credit policies are identified by code (`CP-2025-07`) | Map to the policy version (v1, v2, v3) through `reference.credit_policy_map` | `stg_loans.sql` |
| Days past due must agree with instalments in arrears | Tested, not changed: check `dpd_matches_arrears` fails if they disagree | `sql/tests/18_dpd_matches_arrears.sql` |

The tape feeds `marts.fct_loan_status_monthly`, which adds the arrears bucket, whether each loan has ever been 30+ days past due, and the month's accrued interest.

### 6. Marketing team: `marketing_spend.xlsx`

The growth team's own spreadsheet of monthly spend by channel, typed in by hand at month end.

**Layout:** a title and a note in the first rows, then a header row of months, one row per spend line (Google Ads, Facebook / Instagram, TikTok, Affiliate (cashback), Referral programme, Organic / App store, FD Raya promo (in-app banners), Brand / PR), a TOTAL row and a footnote.

| Problem in the source | Cleaning rule | Where |
|---|---|---|
| Wide layout, a column per month | `UNPIVOT` to one row per line per month; `INCLUDE NULLS` keeps months left blank | `stg_marketing_spend.sql` |
| The header row sits below a title and notes | The loader finds the header row by looking for `Channel` | `src/load.py` |
| Month headers are text (`Sep-24`), except where Excel turned them into dates | Parse both forms | `stg_marketing_spend.sql` |
| Values are numbers, text with separators (`8,018.16`), text with `RM`, `-` for none, or `n/a` | Strip `RM` and separators; `-` is zero; `n/a` stays missing, never zero | `stg_marketing_spend.sql` |
| August 2026's Meta invoice had not arrived (`n/a`) | Cost per customer is left blank for that month rather than understated; check `marketing_invoices_missing` warns | `kpi.growth_monthly` |
| The TOTAL row for January 2026 was typed RM500 too high | Reporting always uses the lines, never the TOTAL row; check `marketing_sheet_total_foots` warns | `stg_marketing_spend.sql` |
| Line labels are the team's own (`Facebook / Instagram`) | Map to channels through `reference.marketing_line_map`; brand and deposit-promotion spend are not acquisition spend | `stg_marketing_spend.sql` |

## 4. Reference data

Lookup tables kept in [`data/reference/`](../data/reference/) and loaded into the `reference` schema. They are maintained by hand, like a bank's own reference data.

| File | What it holds |
|---|---|
| `kpi_catalog.csv` | The 22 KPIs: definition, formula, owner, unit, direction, amber band, target and SQL source |
| `plan_targets.csv` | The monthly plan for the six scorecard KPIs |
| `channels.csv`, `channel_map.csv` | Acquisition channels, and every raw channel label mapped to one |
| `products.csv`, `product_map.csv`, `product_rates.csv` | Products, raw product codes, and rates with their effective dates |
| `campaigns.csv` | The Raya FD promotion |
| `experiments.csv` | The eKYC A/B test: dates, metrics, guardrail and decision rule, written before the test |
| `funnel_steps.csv` | The six sign-up steps in order |
| `credit_policy_map.csv` | Credit policy codes, versions and what each changed |
| `txn_code_map.csv` | Old and new posting engine codes mapped to transaction types |
| `card_status_map.csv`, `entry_mode_map.csv`, `response_code_map.csv`, `merchant_category_map.csv` | Card processor labels and codes |
| `state_map.csv`, `employment_map.csv` | Customer labels mapped to standard values |
| `marketing_line_map.csv` | Spreadsheet lines mapped to channels |

## 5. What the simulator plants

The simulator plants five stories with known answers, so the analysis can be tested: if a method is sound, it should find each one. None of them is hard-coded into the SQL or the analysis.

| # | Story | Where it shows | Found in |
|---|---|---|---|
| 1 | TikTok brings cheap sign-ups whose customers mostly stop using the account | Cost per new against cost per retained customer, by channel | Finding 1 |
| 2 | Many applicants fail the selfie liveness check; a guided flow, A/B tested from February to April 2026, fixes part of it | Funnel drop-off by step; the A/B test | Finding 2 |
| 3 | The Raya FD promotion mostly moves customers' own savings into a costlier deposit, diluting the CASA ratio | CASA ratio, cost of funds, source of promotion money, retention at maturity | Finding 3 |
| 4 | The looser v2 credit policy (July to December 2025) approves loans that fall behind far more often | Vintage curves by policy, roll rates, PAR30 | Finding 4 |
| 5 | Customers who activate their debit card within 30 days are far more likely to stay active | Month-3 activity by card activation, within the same channels | Finding 1 |

And the real-world mess the staging layer has to clean, described source by source above: duplicate events and customers, mixed UTC and local timestamps, label variants, the posting engine's code change, card status updates and resends, late card settlements, DD/MM/YYYY dates, and a hand-kept spreadsheet with text numbers, date headers, a missing invoice and a typing error in its total.
